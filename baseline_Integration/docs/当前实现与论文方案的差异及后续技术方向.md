## 1. 数据集：从相对干净的单语言数据向真实模糊、多语言数据扩展

论文使用 NCVR 2014年和2017年两个时间快照，通过 NCID 对齐同一人员在不同时间的记录。由于姓名可能随时间发生拼写、格式或后缀变化，该数据天然包含一定程度的模糊匹配问题。正样本大多属于完全相同姓名，主要验证协议链路、同态计算正确性和系统性能，不能充分代表真实场景中的模糊姓名变化。

后续数据集将由**干净到模糊、由单语言到多语言**的顺序逐步扩展。第一阶段在现有英文姓名上加入可控扰动，包括字符插入、删除、替换、相邻字符交换、中间名缩写、姓与名顺序变化、空格和标点变化等。

引入真实跨时间或跨机构记录，使用稳定身份标识构造真值，避免仅依赖人工生成的字符串变化。第三阶段进一步扩展到多语言姓名，包括中文姓名、拼音姓名、带重音符号的欧洲姓名、阿拉伯语姓名及其拉丁转写形式。

多语言扩展需要建立统一的规范化流程，例如 Unicode NFKC 规范化、大小写折叠、重音符号处理、语言识别、音译以及原文与转写文本的双通道编码。对于“张伟—ZHANG WEI”“محمد علي—MOHAMED ALI”等记录，可以分别计算字符级、音译级和语音级相似度，再进行加权融合。



## 2. 特征维度：从姓名单字段匹配扩展到多字段实体匹配

**论文和当前实现都主要依据姓名进行匹配**。只是用姓名单一特征，清洗并切分为3-gram，再生成 MinHash 签名。

这种设计适合验证隐私保护模糊姓名匹配协议，但姓名本身并不是可靠的唯一身份标识。不同人员可能具有完全相同的姓名，尤其是在常见姓氏、常见名字或人口规模较大的数据集中。对于同名人员，仅依靠姓名特征时相似度可能接近1，系统无法区分“同一个人”和“姓名相同的不同人员”，从而产生不可避免的误报。

**后续系统需要从姓名匹配扩展为多维度匹配**。可以纳入的字段包括出生日期、地址、电话号码、电子邮箱、证件信息的受保护派生特征，以及机构允许使用的其他身份属性。

姓名可以继续使用字符级 MinHash；地址可以使用分词、字符n-gram或结构化地址编码；出生日期可以使用年、月、日的分层一致性特征；电话号码和邮箱则可以使用精确匹配特征与局部模糊特征的组合。



## 3. 密文打包：从查询维度批处理扩展为 Query × Candidate 二维打包

论文明确提出使用 TenSEAL 和 CKKS batching提升多查询处理效率，但没有给出完整的 slot 排布方式。根据论文逐列执行第二轮匹配的伪代码，其实现主要可以理解为：将多条查询放入同一个密文的不同槽位中，使一个候选列能够同时与多条查询计算，但候选列本身仍然需要逐列处理。
